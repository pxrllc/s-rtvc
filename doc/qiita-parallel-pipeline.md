# 音声会話AIに「間」を持たせる設計思想
## ── LLM待機中に相槌を返す並列パイプラインの構想と実装

---

## はじめに

音声会話AIを自作したことがある人なら、一度は感じたことがあるはずだ。

**「なんか、間が悪い」**

STT（音声認識）が完了し、LLMが考え始め、TTS（音声合成）が生成し、ようやく声が聞こえる。その間、相手は無言だ。処理が速くても1秒以上、モデルや環境によっては3〜5秒の沈黙が続く。

技術的には正しく動いている。でも会話としては、明らかに不自然だ。

この記事では、**「LLMの応答を待つ前に、まず何かを返す」** という設計思想と、それを実現するためのパイプライン構造について書く。実装の詳細はぼかすが、設計の考え方はできるだけ具体的に伝えたい。

---

## 問題の本質：人間の会話に「無音」はない

人間同士の会話を観察すると、聞き手は話し手が話している間、ずっと黙っているわけではない。

- 「うん」「そうそう」「へえ」
- 短い驚きの声
- わずかな相槌

これらは **バックチャネル** と呼ばれ、「聞いていますよ」「続けてください」というシグナルとして機能する。内容的には何も言っていないに等しいが、これがあるとないとでは会話の流暢さがまったく違う。

つまり問題は「LLMの回答が遅い」ことではなく、「**その間に何も返さないこと**」だった。

---

## 構想：2フェーズ応答モデル

この気づきから、応答を2つのフェーズに分けることを考えた。

```
Phase 1: 即時応答（onset）
  → 意図を判定して、文脈に合った短い相槌を即座に返す

Phase 2: 本回答
  → LLMが生成した応答を合成して返す
```

重要なのは、この2つが **直列ではなく並列** で動くことだ。

```
ユーザー発話終了
    │
    ├─→ [意図分類] → [相槌選択] → [即時再生]  ← Phase 1（~数ms）
    │
    └─→ [LLM生成] ─────────────→ [TTS合成] → [再生]  ← Phase 2（~数百ms〜）
```

Phase 1が終わるころにはPhase 2がまだ走っている。相槌が流れている間にLLMが考え、合成が完了したら続けて本回答を再生する。ユーザーからは「すぐに反応して、続けて話してくれる」ように聞こえる。

---

## なぜLLMで意図分類しないのか

「意図分類もLLMでやればいいのでは」という疑問は自然だ。実際、精度だけ見ればそのほうが高い。

しかし今回のシステムでは、**意図分類はPhase 1に属する処理**だ。Phase 1の価値は「即時性」にある。LLMに意図分類を投げた時点で、数百msの遅延が発生し、設計の前提が崩れる。

そこで採用したのは、**高速な文字列マッチングによる意図分類**だ。複数のパターンを同時にスキャンできるアルゴリズムを使い、発話テキストを受け取ってからミリ秒以下で意図カテゴリとスコアを返す。

精度はLLMより低い。ただし誤分類してもPhase 1に影響するのは「相槌の選択」だけだ。会話の本質はPhase 2（LLM）が担保している。**許容できる誤りの範囲内でスピードを取る**、という割り切りだ。

さらに、文末の形（疑問符・感嘆符）、発話の長さ、ネガティブ表現の有無などのルールを組み合わせて、スコアを補正している。これにより「文字列パターンだけでは拾えない文脈」をある程度カバーしている。

---

## 相槌バンクの設計

意図が分類されたら、対応する相槌を選ぶ。ここでも単純な「意図→固定フレーズ」にはしなかった。

### クールダウンと使用頻度管理

同じフレーズが繰り返されると、すぐに機械的に感じられる。そのため各フレーズに「最後に使った時刻」と「使用回数」を持たせ、一定時間内に同じフレーズが出ないよう制御している。

### 信頼度による切り替え

意図分類のスコアが低い場合、つまり「何を言っているか判断しきれない」場合は、意図に特化した相槌ではなく汎用の傾聴フレーズ（「うん」「そうなんだ」など）に切り替える。文脈外の強いリアクションが出てしまうよりも、中立的に聞いているほうが自然だからだ。

### 感情トレンドとの連動

直近の会話が続けてネガティブな流れだと判定された場合は、強めのポジティブリアクションを抑制する。話が暗いのに「それ最高！」と返ってくるような違和感を避けるためだ。

---

## キャッシュ戦略：相槌は事前合成する

Phase 1の命は速さだ。相槌のTTS合成をリアルタイムに行うと、それだけで数百msかかる。

そこで、バンクに登録されている全フレーズを**事前にWAVファイルとして生成**し、アプリ起動時にメモリに展開しておく。ヒットしたフレーズの再生は、展開済みのFloat32配列をそのままオーディオバッファに送るだけなので、数ms以下で完了する。

事前合成のコストは開発サイクルの中で一度だけ払えばいい。ユーザー体験の「速さ」に対して、開発時間で払うトレードオフだ。

---

## LLMへのコンテキスト注入

Phase 2のLLMには、単純にユーザーの発話を渡すだけではない。会話の流れをより正確に伝えるために、システムプロンプトに動的なコンテキストを注入している。

具体的には：

- **セッション内の記憶**：直近の発話から抽出したキーワード、話題の流れ、感情の傾向
- **セッション間の記憶**：過去のセッションで繰り返し登場したトピック、ユーザーの関心領域

これにより、LLMは「今何の話をしているか」だけでなく「この人はどんな話をよくするか」を踏まえた回答を生成できる。記憶の永続化はJSONLファイルとJSONファイルで行い、外部サービスへの依存を避けた。

---

## TTS抽象化：声を選べる設計

音声合成エンジンは複数の選択肢がある。今回はエンジンをインターフェースとして抽象化し、設定ファイルを書き換えるだけで切り替えられる設計にした。

調査の中で、あるエンジンがVOICEVOX互換と説明されていたにもかかわらず、実際にはAPIのパス構造も呼び出し手順も独自形式だったことがあった。ドキュメントではなく実際にエンドポイントを叩いて仕様を確認し、専用クライアントを書くことになった。「互換」という言葉は過信しないほうがいい、という教訓を得た。

## 実装を振り返って

システムの全体像を図にするとこうなる。

```
マイク入力
    ↓
VAD（発話検出）
    ↓
STT（音声認識）
    ↓
┌───────────────────────────────────────┐
│          並列パイプライン              │
│                                       │
│  [意図分類] → [相槌選択] → [即時再生] │ ← Phase 1
│                                       │
│  [コンテキスト構築]                   │
│       ↓                               │
│  [LLM生成] → [TTS合成] → [本回答再生] │ ← Phase 2
└───────────────────────────────────────┘
    ↓
セッション終了時: 記憶の永続化
```

この構成で、ユーザーが話し終えてから**数十ms以内に何らかの音声が返り**、続けてLLMの回答が流れる。沈黙の時間はほぼゼロになった。

---

## おわりに

今回の設計で意識したのは、「**AIの賢さより、会話のリズム**」という優先順位だ。

どれだけ高精度なLLMを使っても、返答が遅ければ会話としての体験は壊れる。逆に、相槌が的外れでも、「すぐに反応してくれる」という感覚があれば、人はそれを許容することが多い。

AIの会話能力を上げることと、会話体験を上げることは、必ずしも同じではない。技術の選択は、何を優先するかによって変わってくる。

まだ荒削りな部分も多いが、この設計思想が誰かの参考になれば幸いだ。
